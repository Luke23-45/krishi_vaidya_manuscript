\chapter{INTRODUCTION}

\ChapterSection{Introduction}

A rice farmer in the Terai plains photographs a cluster of brown lesions spreading across her
crop's leaves. She needs to know whether the damage is bacterial leaf blight, brown spot, or
blast---and she needs to know within hours, not days, because the wrong treatment applied too
late can mean the difference between a manageable loss and a ruined harvest. In Nepal, where
agriculture accounts for approximately one-quarter of national GDP and directly sustains the
majority of rural households \parencite{moaldAgricultureStats2080,nsoAgricultureCensus2021},
this scenario repeats across millions of smallholdings every growing season.

This is the core problem: farmers need diagnoses faster than the available expert channels can
deliver them. Traditional diagnosis depends on extension
workers, agro-vet consultants, or laboratory confirmation---channels that are valuable but
geographically sparse, seasonally overloaded, and often unreachable at the moment a farmer
first observes symptoms in the field. The FAO estimates that plant pests and diseases can
destroy up to 40 percent of global crop production annually, with actual loss depending on crop,
location, season, and management practice \parencite{faoPlantHealthLosses}. Nepal's
topographic diversity, settlement patterns, and variable connectivity amplify this challenge
for smallholder farmers who may possess a smartphone and a crop image but lack immediate access
to a trained plant-health expert \parencite{khatriNepalDigitalAgri2023}.

Part of the answer lies in computer vision. Object detection can locate relevant plant
structures within complex field images, and vision-language models can generate structured
diagnostic interpretations from visual input. The smartphone provides the interface: it is
the most realistic access point for field-level users in Nepal's agricultural context
\parencite{faoNepalDigitalAgriculture}. But a practical system must handle image capture,
model inference, output parsing, backend validation, advisory generation, local record keeping,
offline resilience, and uncertainty communication---engineering that extends well beyond model
training alone.

Krishi Vaidya is a final-year B.Sc.\ CSIT project that addresses this end-to-end workflow. It
composes four subsystems: a YOLO-based plant-part detector, a Qwen-based vision-language model
for disease interpretation, an Express/Mongoose backend API for orchestration and persistence,
and a React Native/Expo mobile application for farmer-facing interaction.

\ChapterSection{Problem Statement}

Existing digital approaches typically address isolated aspects of this problem: image
classification without advisory output, model training without deployment evaluation, or mobile
interfaces without offline resilience.

The research problem addressed by this project is:

\begin{quote}
Can an integrated system combining object detection, vision-language interpretation, backend
orchestration, and an offline-aware mobile application be designed, implemented, and evaluated
to support image-based crop-health diagnosis and structured advisory output for the Nepalese
agricultural context?
\end{quote}

\ChapterSubsection{Visual detection challenge}

Crop images contain multiple plant structures, and disease-related reasoning often depends on
which part of the plant is visible. Without part-level detection, the system treats an entire
field image as a single classification input, losing spatial context. The project handles this
by training a YOLOv8 nano detector on a curated multi-crop plant-part dataset with eleven
agricultural object classes, then evaluating detection performance across thresholds and
quantized deployment variants.

\ChapterSubsection{Disease interpretation challenge}

Disease diagnosis requires more than detecting plant objects. The system must interpret visual
evidence and produce structured information---disease name, confidence, severity, treatment
guidance---that downstream components can parse, validate, and display. This challenge is
addressed through a LoRA-adapted VLM pipeline trained on structured image-text records, with
evaluation focused not only on classification accuracy but also on whether generated outputs
can be reliably parsed into canonical labels.

\ChapterSubsection{Mobile access and advisory workflow challenge}

The mobile application must support image capture, diagnosis submission, offline record keeping,
synchronization, crop management, and understandable result presentation. The backend must
protect the API, validate requests, orchestrate inference, store records, and return consistent
structured responses. Both layers are implemented as full application components rather than
limiting the project to model training alone.

\ChapterSection{Objectives}

\ChapterSubsection{General objective}

To design, implement, and evaluate an integrated crop-health diagnosis-support system for
Nepalese smallholder farmers. The system uses object detection, vision-language modelling,
backend services, and a mobile application to support image-based disease interpretation and
structured advisory output.

\ChapterSubsection{Specific objectives}

\begin{enumerate}[label=\arabic*.]
\item To investigate the viability of lightweight object detection for agricultural plant-part
localization by curating a multi-source dataset, training a YOLOv8 nano detector, and
evaluating detection performance across confidence thresholds and quantized deployment variants.
\item To evaluate LoRA-based fine-tuning of a vision-language model for structured disease
interpretation by preparing a Qwen-format dataset, training with quantized adapters, and
assessing both classification accuracy and output parseability.
\item To implement a layered backend API that orchestrates authentication, crop records, scan
handling, diagnosis inference, advisory generation, and validation within a documented
architectural pattern.
\item To implement an offline-aware mobile application that supports farmer-facing scan workflow,
bilingual output, local persistence, synchronization infrastructure, and crop-management
record keeping.
\item To integrate the subsystems into a documented diagnosis workflow and evaluate the
integrated path through runtime-verified contracts, generated architecture diagrams, and
completed distributed deployment evidence.
\end{enumerate}

\ChapterSection{Scope and Limitation}

The \textbf{model scope} includes YOLO object detection for plant-part localization across
eleven agricultural classes and VLM-based disease interpretation for a subset of crop-disease
categories derived from the PlantVillage corpus. The \textbf{backend scope} includes the
implemented Express/Mongoose service architecture, scan and diagnosis workflow, advisory
response handling, authentication, security middleware, validation, and available test coverage.
The \textbf{mobile scope} includes the React Native/Expo application with scan workflow, local
SQLite persistence, offline-aware behavior, synchronization infrastructure, crop and task
records, bilingual interface, and on-device TFLite model assets.

The following boundary conditions apply:

\begin{enumerate}[label=\arabic*.]
\item The project does not claim to produce a certified, agronomically validated, or
government-approved diagnosis system. It is a research and engineering prototype suitable
for demonstrating integrated software and model development.
\item The YOLO dataset, though large and curated, exhibits significant class imbalance; some
classes have orders of magnitude fewer annotations than others.
\item The VLM pipeline is implemented and measurable. Because it was trained as a
compute-constrained three-epoch LoRA experiment on curated online image-text data, its current
metrics reflect a limited training run, not an optimized model.
\item Due to time and budget constraints, automated backend test coverage prioritizes the core scan domain; external API integrations and standard CRUD endpoints were tested manually during development.
\item The mobile application's integration architecture, including its offline-to-online recovery mechanisms, has been thoroughly validated through physical-device testing and distributed runtime measurements.
\item The advisory output has not been validated by certified agricultural experts and must
not substitute for expert consultation.
\end{enumerate}

\ChapterSection{Development Methodology}

Krishi Vaidya follows an iterative development methodology organized around four phases:
analysis, design, implementation, and testing.

\ChapterSubsection{Analysis}

System requirements were derived from the intended farmer-facing diagnosis workflow rather
than from model capabilities alone. Nine functional requirements cover onboarding, crop-record
management, image capture, backend authentication and image validation, VLM inference,
structured response assembly, persistence, and offline-aware behavior. Eight non-functional
requirements address usability, reliability, security, maintainability, performance,
testability, offline support, and safety constraints.

\ChapterSubsection{Design}

Requirements were mapped into four cooperating subsystems. For object detection, YOLOv8 nano
was configured for plant-part localization across eleven agricultural classes, trained on a
curated 30,981-image, 147,467-annotation dataset. For disease interpretation,
Qwen2.5-VL-3B-Instruct was selected with LoRA adapters and 4-bit NF4 quantization to produce
structured JSON diagnostic labels. The backend was designed as a layered TypeScript/Express API
with separate configuration, middleware, routing, controller, service, repository, and model
concerns, exposing nine versioned route groups. The mobile application was designed around a
local-first approach using React Native/Expo, with SQLite persistence, a network-aware
diagnosis hook, and on-device TFLite model support.

\ChapterSubsection{Implementation}

Each subsystem was built and integrated incrementally. The YOLO pipeline covers dataset
curation, 100-epoch training at 640-pixel resolution, confidence-threshold analysis, and
TFLite export in FP32, FP16, and INT8 precision variants. The VLM pipeline covers
PlantVillage-derived dataset construction, three-epoch supervised fine-tuning on an NVIDIA
L4 GPU, and FastAPI inference gateway deployment with JWT authentication. The backend
implements eight API domains---diagnosis, authentication, users, scans, crops, tasks, notes,
and advisories---with Cloudinary storage, Zod-validated configuration, and an explicit
dependency container. The mobile application implements the scan capture workflow, crop-plot
management, bilingual advisory presentation, SQLite offline queuing, and synchronization
infrastructure.

\ChapterSubsection{Testing and Validation}

Validation was carried out at both the component and system-boundary levels using
project-workspace artifacts. The YOLO subsystem was assessed through a confidence-threshold
sweep from 0.05 to 0.95, a four-variant deployment comparison, per-class F1 breakdowns, and
confusion-matrix analysis. The VLM subsystem was evaluated on a held-out 798-example test
split, measuring both classification accuracy and the parseability rate of generated outputs.
Backend scan behavior is covered by 21 unit tests and 26 route integration tests running
against an in-memory MongoDB instance. Mobile workflows were validated through source
inspection and physical-device testing on Android. A distributed deployment---VLM gateway on
Lightning.ai, database on Supabase, backend served via ngrok---verified the complete request
lifecycle including offline queue recovery. Every result claim in the manuscript is tied to
code, generated outputs, or measured model results.
