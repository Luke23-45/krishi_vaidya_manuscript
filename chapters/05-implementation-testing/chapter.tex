\ChapterSubsection{Implementation Details of Modules}

Four modules divide the work. The YOLO module handles dataset preparation, detector training,
threshold evaluation, and TFLite export. For the VLM, we constructed Qwen-format image-text
records, fine-tuned Qwen2.5-VL-3B with LoRA adapters, served inference through a FastAPI
gateway, and validated canonical-label parseability. The backend implements route groups, validation,
authentication, persistence, VLM inference calls, advisory generation, and diagnosis response
assembly. The mobile frontend provides onboarding, scan capture, preview and editing, network-aware
diagnosis, SQLite-backed offline queues, crop records, result display, reminders, sharing, PDF
export, and on-device TFLite model loading.

The rice panicle bias has a structural cause. Although 115,046 annotations make it the largest
class by count, these objects are small, clustered, and visually dense. Lightweight YOLO
architectures lose spatial detail at this scale, a known difficulty in agricultural small-object
detection~\parencite{zhengSmallObjDetAgri2023}. Addressing this class needs higher-resolution
training, targeted augmentation for small clustered objects, or both. Given these class-specific
gaps, YOLO detections feed the downstream VLM diagnosis rather than standing alone as disease
labels.

Several factors compound to produce the high parse-error rate: the small 3B-parameter base,
LoRA-only adaptation, a three-epoch budget, variable online-source images, mixed prompt

stronger format supervision, or post-generation repair~\parencite{paleyes2022MLSystemsChallenges}
are the natural next steps.

\subsubsection{Confusion Matrix and Prediction Distribution}

Figures~\ref{fig:vlm-confusion-matrix} and~\ref{fig:vlm-inference-diagnostics} show prediction
distribution and latency patterns. Parse errors dominate the matrix, not inter-class
confusion---the model fails to produce parseable answers more often than it confuses one disease
for another. Parse-error predictions also run slower (median 7.32~s vs.\ 5.32--6.67~s for
successful labels), so fixing output format would improve both accuracy and throughput. Until
those fixes land, the VLM cannot serve as an autonomous disease classifier.

costs, and we manually checked authentication, crops, tasks, notes, and advisory routes too.

\subsubsection{Current Limitations}

Two design limitations remain. First, diagnosis processing is synchronous despite Redis carrying
BullMQ-compatible options; we have not yet implemented background job processing.
Second, the system depends on upstream VLM and Google AI availability, and automated mocks for
those external services do not exist yet.

\subsubsection{Model Deployment and Verification}

Our app packages TFLite model assets in int8, fp16, and fp32 precision variants, exposed as a

runtime precision switching. A mobile parser enforces the 11-class plant-part taxonomy from

diagnosis flow, offline recovery, and model-asset loading.

\ChapterSubsection{Integrated System Discussion}

\subsubsection{End-to-End Integration Outcome}

Our integration boundary is clean: the mobile app never calls the VLM or advisory services
directly, the backend never surfaces raw model text, and each boundary validates or normalizes
data before forwarding.

We ran end-to-end validation on a distributed deployment---VLM on Lightning.ai, database on
Supabase, backend via ngrok---covering the full request lifecycle including offline queue
recovery.

\subsubsection{Limitations and Evidence Gaps}

A limited training budget constrained the VLM, and the backend schema masks raw outputs but cannot
compensate for a three-epoch model's prediction quality. Automated integration tests cover the
scan domain and VLM API routes; secondary workflows and load scaling remain untested.

\subsubsection{Model-Level Interpretation}

Between the two ML components, YOLO is the more mature; the VLM pipeline is complete but the
three-epoch model is not yet a reliable classifier. The bottleneck is training duration and
decoding control, not the VLM approach.

\subsubsection{System-Level Interpretation}

Reliability controls---image validation, readiness checks, JWT authentication, schema
enforcement, offline queuing---limit how far an invalid or unavailable component can propagate
to the farmer, but they do not resolve agronomic safety issues: model uncertainty,
field-image variability, and pesticide recommendation risk.
