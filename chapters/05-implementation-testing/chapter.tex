\ChapterSubsection{Implementation Details of Modules}

The implementation is organized into four major modules. The YOLO module provides plant-part
object detection and deployment-variant evaluation. The VLM module provides disease-oriented
vision-language fine-tuning, inference serving, prediction parsing, and metric generation. The
backend module provides authentication, crop records, scan management, diagnosis orchestration,
advisory response handling, validation, repositories, and route tests. The mobile module provides
onboarding, scan capture, image editing, result display, crop management, local persistence,
settings, accessibility options, and offline-aware behavior.

\subsubsection{Validation Strategy}

Testing and validation for Krishi Vaidya were organized around the actual structure of the system.
The project is not validated by one metric alone because it contains trained models, an inference
gateway, a backend API, a mobile application, and an integrated diagnosis workflow. Therefore, the
validation strategy separates five kinds of evidence: model-performance validation, dataset and
pipeline integrity checks, automated backend/API tests, mobile source and inference checks, and
integration-boundary verification.

This separation is important for accuracy. A high YOLO score does not prove that the backend is
correct. A passing backend scan test does not prove that the mobile app works on a physical
device. A valid VLM inference API test does not prove that the model predictions are accurate.
Each validation result is therefore interpreted according to what it actually verifies. The
remaining evidence gaps are described in the subsections that follow.

\subsubsection{YOLO Validation}

The YOLO subsystem has the strongest quantitative detection evidence in the project. Its
validation includes training dynamics, best-epoch metrics, validation on the validation
split, threshold analysis, quantized model comparison, per-class metrics, latency measurements,
confusion matrix outputs, and error-category analysis. The validation artifacts are stored under
the YOLO result directories and were converted into manuscript-ready figures and tables in the
YOLO manuscript data folder.



The YOLO training metrics show the training trajectory across 100 epochs. The best recorded
training summary used in the manuscript reports precision 0.71717, recall 0.74868, mAP50
0.76163, and mAP50-95 0.60191 at epoch 100. Thorough validation provides an additional evaluation
view using the validation images and labels. In the baseline validation summary, 3,527
images and 20,443 ground-truth objects were evaluated, producing 3,701 true positives, 171 false
positives, and 16,742 false negatives at confidence threshold 0.25 and IoU threshold 0.5. This
corresponds to precision 0.69286, recall 0.79522, F1 0.74016, and mean inference time
12.609 ms in that validation run.

\subsubsection{VLM Validation}

The VLM subsystem was validated at two levels: dataset/pipeline validation and prediction
validation. Dataset validation checked the prepared Qwen-format records and image references. The
recorded dataset-validation summary reports 13,294 images found, 6,647 Qwen records, zero decode
failures, zero missing Qwen images, and zero recorded issues. This supports the claim that the
exported VLM dataset was structurally usable for training and evaluation.

Prediction validation was more severe. The independent test split contained 798 examples across
13 classes. The recorded prediction metrics report accuracy 0.13033, macro precision 0.52317,
macro recall 0.18342, macro F1 0.24655, and 540 parse-error predictions. These values are already
discussed in the VLM results section, but they are repeated here as validation evidence because
they define the current reliability boundary of the VLM component. The validation does not support
a claim that the current fine-tuned VLM is already diagnostically strong. It supports a more
careful claim: the VLM training and evaluation pipeline exists, the dataset export is structurally
validated, and the current model behavior exposes a serious parseability and prediction-quality
limitation that the final system must acknowledge.

The VLM repository also contains automated tests for dataset normalization, deduplication, source
adapters, split creation, manifest behavior, training data loading, training runtime compatibility,
runtime accelerator configuration, inference runtime configuration, inference batching,
performance batch-size resolution, validation metric calculation, prediction parsing, and the
FastAPI inference gateway. Across the visible VLM test files, there are 46 Python test functions,
including 11 tests dedicated to the inference API route behavior.

\subsubsection{VLM Inference API Validation}

The VLM inference gateway has a focused API test suite. These tests use a stubbed vLLM client and
FastAPI test client rather than loading the full model. This is appropriate for route-contract
validation because the purpose is to verify HTTP behavior, authentication handling, request
validation, and error mapping without requiring GPU inference in the test process.

The inference API tests cover liveness, readiness failure, readiness success, missing
authentication, insufficient JWT scope, invalid base64 image rejection, successful inference
response mapping, timeout/unreachable/backend-failure mapping, environment setting loading,
settings-cache overrides, and configured rate-limit behavior. This gives the manuscript concrete
evidence that the inference gateway is not only a conceptual endpoint. Its API contract and
failure behavior are represented in automated tests.

\subsubsection{Backend Validation}

The backend validation evidence is strongest for the scan domain. The available unit tests focus
on the scan service, and the integration tests focus on scan routes. The test setup uses
MongoDB Memory Server, clears database collections between tests, and configures test environment
variables for JWT, Cloudinary, Redis, email, MongoDB, and server port. This allows scan behavior
to be tested without depending on a persistent external MongoDB instance.

The scan service unit tests cover scan creation, offline scan creation, owner-scoped retrieval,
non-existent scan handling, cross-user access protection, pagination, status filtering,
crop-type filtering, update behavior, soft deletion, statistics, resolution creation, duplicate
resolution rejection, resolution retrieval, follow-up linkage, related scans, and grouping. The
scan route integration tests cover authentication requirement, paginated retrieval, filtering,
pagination, statistics, grouping, invalid group-by validation, scan lookup, missing-scan behavior,
status retrieval, resolution creation, duplicate-resolution protection, follow-up linkage, and
related-scan lookup.

There are 21 visible scan-service unit test cases and 26 visible scan-route integration test cases.
This is meaningful evidence for the scan domain, but it is not complete backend coverage.
Test coverage is strategically concentrated on the core scan domain. The backend is
therefore partially automated-tested: scan behavior is well represented, while manual
validation and integration checks secure the remaining authentication, crop, task, note, advisory,
and diagnosis paths.

Integration validation is completed through source verification, contract review, and distributed

End-to-end validation was performed using a distributed deployment architecture. This setup verified the complete mobile-to-cloud request lifecycle, including request validation, model inference, structured advisory generation, and offline-to-online recovery.

which indicates that the selected run did not terminate early before completing the configured
training schedule.

Figure~\ref{fig:yolo-training-dynamics} presents the training dynamics. The curve shows the
relationship between loss reduction and detection metrics across the training process. The model
improves substantially from the early epochs and stabilizes toward the later part of training.

\subsubsection{Best-Epoch Performance}

Table~\ref{tab:yolo-training-dynamics-summary} summarizes the final and best-epoch values. The
model achieved precision of 0.7172, recall of 0.7487, F1-score of 0.7326, mAP@50 of 0.7616, and
mAP@50-95 of 0.6019. The recall is slightly higher than precision, indicating that the detector
leans toward object discovery over conservative filtering. For the Krishi Vaidya workflow, this
is a useful property for a first-stage visual detector: missed plant regions cannot be analyzed
downstream, while false or uncertain detections can still be filtered through thresholds,
downstream model behavior, or user interaction.

The difference between mAP@50 and mAP@50-95 also matters. mAP@50 measures whether detected
objects overlap the ground truth at a moderate threshold, while mAP@50-95 requires stronger
localization across stricter IoU thresholds. The lower mAP@50-95 value indicates that localization
quality remains more difficult than basic object discovery, especially in a dataset with strongly
uneven class frequency and object scales.

The threshold sweep also shows why a high confidence threshold is unsuitable for this detector.
At 0.95, recall falls to 0.0776 and F1-score falls to 0.1208. This would remove most detections
and make the detector ineffective as a first-stage model. Conversely, the 0.05 threshold has
higher recall but lower precision than the selected threshold. The 0.10 operating point therefore
provides a practical balance between keeping enough detections and controlling false positives.

final selections require on-device Android profiling, as current latencies reflect \texttt{cuda:0}
measurements.

architecture or augmentation choices designed for small, clustered objects.

\subsubsection{Summary of YOLO Findings}

The YOLO component provides a complete, evidence-backed object-detection subsystem for Krishi
Vaidya. The trained detector achieved F1-score of 0.7326, mAP@50 of 0.7616, and mAP@50-95 of
0.6019 at the best recorded epoch. The threshold sweep identifies 0.10 as the best F1 operating
point among the tested confidence thresholds. The deployment comparison shows that TFLite variants
preserve useful detection performance, with INT8 providing the smallest model size and FP16
providing a closer accuracy-size compromise.

The main limitation is class-specific reliability. The detector performs much better for some
classes than others, and dense or underrepresented structures require further improvement. For the
larger Krishi Vaidya system, this means the YOLO model is suitable as a visual detection component,
but its outputs should be treated as supporting evidence rather than as the sole basis for disease
diagnosis.

\subsubsection{Summary of VLM Findings}

The VLM work demonstrates that Krishi Vaidya includes a real fine-tuned vision-language component,
not only a detector or mobile interface. The model was fine-tuned with LoRA adapters on
Qwen2.5-VL-3B-Instruct using 4-bit NF4 quantization and completed the training run within the
available NVIDIA L4 resource envelope. The training objective was fitted successfully, as shown by
the low final evaluation loss and high token accuracy.

However, the prediction results show that the current VLM is unreliable as an autonomous
structured disease classifier. The major limitation is parseability: 540 of 798 test predictions
could not be parsed into a canonical label. The model also shows class-level weaknesses, especially
for maize common rust, potato healthy, and tomato early blight, and it can emit labels outside the
expected test label set. For the larger Krishi Vaidya system, the VLM should therefore be described
as a fine-tuned diagnostic component with clear current limitations. Its next improvement step is
not simply more training; it requires stricter output control, improved prompt consistency,
possibly constrained decoding or post-processing, and targeted correction of weak classes.

\ChapterSubsection{Backend Domain Discussion}

\subsubsection{Authentication and User Management}

The authentication implementation supports registration, login, access-token refresh, logout,
logout from all devices, OTP sending, OTP verification, forgot-password, and password reset. The
password policy requires at least eight characters and at least one uppercase letter, one
lowercase letter, and one number. Refresh tokens are not stored as plain text; instead, they are
represented as hashed records linked to lookup identifiers and revocation states. This design
reduces the impact of token leakage, which is important because refresh credentials are
longer-lived than access tokens.

User management includes profile retrieval and update, profile-picture upload, password change,
account deletion, and push-token add/remove operations. The profile schema includes bilingual and
Nepal-specific fields such as Nepali name, preferred language, ecological region, province,
district, municipality, ward, latitude, and longitude. It also includes theme and color-blind mode
preferences, which shows that the backend stores application-level preference state rather than
only authentication data.

\subsubsection{Scan Lifecycle}

The scan domain is the most complete persistence-backed workflow in the backend. A scan stores the
uploaded image URI, crop metadata, status, result object, notes, tags, offline flag, client-created
timestamp, deletion state, and optional processing timestamps. The scan service uploads images to
Cloudinary before creating scan records. It also supports scan retrieval, pagination, filtering by
status and crop type, soft deletion, batch deletion, grouped views, related scans, status checks,
scan resolution, resolution retrieval, follow-up linkage, pending-scan retrieval, offline-scan
retrieval, offline scan synchronization, result updates, and failed-scan marking.

The scan-resolution model introduces a post-diagnosis persistence layer. A completed scan can be
marked as treated, resolved naturally, crop removed, or as a false positive. Treatment text,
notes, and follow-up scan identifiers can be explicitly linked. By tracking intervention
outcomes, the architecture creates a path for later evaluation of whether recommendations were
adopted and whether the crop condition improved.

\subsubsection{Crop, Task, Note, and Advisory Management}

Crop plots represent the farmer's managed crop areas. Each plot stores crop type, variety, region,
district, optional location, area value and unit, planting date, expected harvest date, growth
stage, stage progress, health status, archive state, and soft-delete state. The crop routes support
creation, retrieval, filtering, archive/unarchive actions, growth-stage updates, and health-status
updates.

Tasks provide a scheduling layer around crop management. The task model supports categories such as
watering, fertilizing, spraying, weeding, pruning, harvesting, soil preparation, scouting, and other
tasks. Each task has a due date, completion state, priority, and optional auto-generated flag. The
implemented routes expose pending, overdue, upcoming, plot-specific, batch, completion, and
uncompletion operations.

Notes provide a record-keeping layer. A note is linked to a crop plot and can optionally be linked
to a scan. It stores note type, title, body, image URIs, public image identifiers, tags, and
soft-delete state. The implementation permits image attachment and removal after note creation,
which supports field observations that may need additional photographic evidence over time.

Advisories provide a notification-like layer for crop decisions. The advisory model supports
weather alerts, irrigation needs, fertilizer reminders, pest risk, disease risk, harvest windows,
spray windows, frost warnings, and stage transitions. Advisories include severity, bilingual title
and description fields, optional action labels, generated time, dismiss state, and expiry. The
model uses an expiry index, which allows expired advisories to be cleaned up automatically.

\ChapterSubsection{Backend Diagnosis Integration Discussion}

\subsubsection{Structured Diagnosis Response}

Rather than forwarding raw autoregressive VLM text to the mobile client, the backend diagnosis
pipeline enforces a strict response schema encapsulating disease names, bilingual fields, taxonomy,
crop context, confidence, out-of-distribution flags, etiology, and actionable advisories.

This architectural boundary guarantees predictable fields for UI rendering and decision support.
Crucially, validating the schema prior to client transport mitigates the risk of surfacing
hallucinated or misformatted generated text to the user-facing interface.

\subsubsection{Confidence and Out-of-Distribution Handling}

The backend maps clamped confidence values (0 to 1) into four tiers: high, medium, low, and
out-of-distribution (\texttt{ood}). The \texttt{ood} tier applies when explicitly flagged or if
confidence falls below 0.30. To prevent payload overload, alternative diagnoses are restricted
to medium or low confidence tiers, allowing uncertain predictions to convey broader possibilities.

While this structured advisory layer provides an integration safeguard, its efficacy relies
on upstream VLM reliability. Given the high parse-error rates observed during evaluation, the
backend schema mitigates communication risks but cannot resolve underlying VLM inaccuracies.

\ChapterSubsection{Integrated System Discussion}

\subsubsection{End-to-End Integration Outcome}

The integrated Krishi Vaidya system combines mobile image capture, backend orchestration, VLM
prediction, structured advisory generation, and local farmer-facing result handling. The
implementation is not a collection of disconnected demonstrations. The mobile app contains the
scan workflow and result workflow; the backend exposes the diagnosis route; the VLM gateway
exposes readiness and inference endpoints; the advisory client transforms model context into a
schema-validated advisory; and the mobile result view consumes the returned structure for display,
history, reminders, feedback, voice output, and PDF export.

The most important integration result is the separation of responsibilities. The mobile app does
not directly call the VLM service or the Google AI service. The backend does not present raw VLM
text to the farmer. The VLM gateway does not decide how treatment should be shown in the app. Each
component has a defined boundary, and the data passed across those boundaries is validated or
normalized before it moves to the next stage. This structure reduces coupling and makes the system
easier to reason about during manuscript writing and future improvement.

\subsubsection{Data Contract Strengths}

The backend-to-mobile response is the strongest formal contract in the integrated system. It
contains request identifier, timestamp, disease fields, crop, confidence, confidence tier,
out-of-distribution flag, symptom descriptions, advisory arrays, processing time, and model
version. The advisory object separates treatment steps, prevention tips, safety warnings, organic
alternatives, and source URLs. This contract gives the mobile app predictable fields for display
and reduces the risk of placing unconstrained model output directly in front of the user.

The backend-to-VLM boundary is also controlled. The backend checks readiness before inference,
sends base64 image data and a deterministic prompt, limits generation length, sets temperature to
zero, disables sampling, and includes the same request identifier used by the backend response.
The VLM gateway validates authentication, image source shape, image validity, and rate limits. It
returns latency and token counts, which can later be used for deployment reporting.

The advisory-generation boundary adds another safeguard. The backend does not accept arbitrary
text as final treatment advice. The advisory client requires the Google AI response to match a
schema before returning it. It also instructs the model to produce Nepali and English fields, to
avoid fabricated citations, to include uncertainty behavior, and to avoid unsafe pesticide advice.
This does not make the output clinically or agronomically perfect, but it provides an important
engineering control around a generative step.

\subsubsection{Offline and Degraded-Network Behavior}

The integrated workflow is designed for unstable connectivity. The mobile diagnosis hook has
separate behavior for online, slow, and offline network states. In a normal online state, it calls
the backend. In a slow state, it attempts the backend request but falls back after five seconds. In
an offline state, it queues the scan immediately. This design acknowledges a practical constraint:
the intended users may be in agricultural field environments where network access is unreliable.

The offline path is not only a UI message. It writes the scan into the local queue, inserts a
pending scan record into history, and creates a high-priority sync queue item. If cached advisory
data exists for the crop, the app can return a cached result while retaining the queued scan for a
future cloud diagnosis. The implementation therefore supports partial usefulness during
connectivity loss while keeping the cloud path available when the network returns.

The remaining limitation is that full two-way synchronization is currently restricted to core queued workflows.
The sync manager has the structure for queued operations, retry state, network monitoring,
app-resume synchronization, and periodic synchronization, but some generic table-push behavior is
still represented as local status updates until matching backend handlers are completed. The
current evidence therefore supports offline-aware infrastructure, not complete production-grade
bidirectional synchronization.

\subsubsection{Reliability Controls Across the Integrated Path}

Reliability is handled through multiple layers rather than a single validation point. The mobile
client checks that the image URI is usable before building the request. The backend upload route
uses single-image upload middleware. The backend validation service checks file presence, file
content, MIME consistency, image format, image dimensions, and maximum size. The VLM client checks
service readiness and applies request timeouts. The VLM gateway validates JWT scope and image
payloads. The advisory client retries configured failures and validates its final JSON schema.
The mobile result view also normalizes advisory arrays to avoid downstream crashes when optional
advisory fields are missing.

\ChapterSubsection{Cross-System Results Discussion and Limitations}

\subsubsection{Synthesis of Major Results as a Design-Science Contribution}

The principal outcome of Krishi Vaidya is not merely a software artifact, but a design-science
contribution to the architecture of agricultural advisory systems. The integrated
multi-component system yields evidence across the model, backend, mobile, and integration
layers. The YOLO subsystem provides the strongest quantitative modeling result, including
threshold analysis and quantized deployment profiling. The VLM subsystem provides a complete
fine-tuning pipeline while identifying structured parseability as a critical reliability
bottleneck. The backend subsystem implements an orchestration boundary that validates uploads,
bridges ML microservices, and generates schema-enforced advisories. The mobile application
implements a local-first \parencite{kleppmannLocalFirst2019} farmer-facing interface with
offline-aware diagnostic queuing, longitudinal crop management, and localized result rendering.

The strongest overarching contribution of this research is therefore architectural. By
constructing a crop-health support pipeline from field image capture to a schema-validated,
bilingual advisory report, Krishi Vaidya makes visible the ``hidden technical debt''
\parencite{sculleyMLTechDebt2015} between a trained classifier and a deployed application. While
much of the existing literature stops at reporting classification accuracy
\parencite{liu2021plantDiseaseReview, wangAgriLLaVA2024}, Krishi Vaidya documents the additional
engineering required to make model output practically usable: defensive backend validation,
structured response assembly, resilient local-first mobile persistence, and farmer-facing
linguistic translation.

\subsubsection{Model-Level Interpretation}

The YOLO model results indicate that the object-detection component is the most mature machine
learning part of the project. Its metrics are not perfect, but they are supported by multiple
forms of evidence: training dynamics, validation, threshold analysis, quantized deployment
comparison, latency measurements, and error analysis. This allows the manuscript to discuss
realistic deployment tradeoffs instead of only reporting a single final accuracy number.

The VLM results must be interpreted differently. The VLM work is substantial because it includes
dataset construction, Qwen-format export, LoRA fine-tuning, quantized training, inference
infrastructure, dataset validation, and prediction evaluation. However, the independent prediction
metrics show that the current VLM is unreliable as a final
diagnostic authority. The high parse-error count is especially important because the backend and
mobile app depend on structured fields. A model that often fails to produce parseable output can
still be useful as a research artifact, but it must not be overclaimed as a dependable diagnosis
engine.

The correct interpretation is that the project has one relatively stronger model component and
one exploratory VLM component with limited current reliability. The YOLO section supports confidence in the
object-detection work. The VLM section supports confidence in the pipeline and exposes the next
research problem: improving structured multimodal disease prediction.

\subsubsection{System-Level Interpretation}

The backend and mobile results show that the project was engineered as a system rather than as an
isolated notebook experiment. The backend provides request validation, route organization,
repository-backed domain logic, image upload support, token/session handling, scan lifecycle
management, crop/task/note/advisory records, VLM inference bridging, and advisory-schema
validation. The mobile app provides the user-facing workflow required to apply those backend
features in a field setting.

The important system-level finding is that the engineering architecture is fully supported
by runtime evidence. The source code shows a serious architecture, and the distributed deployment
metrics prove exactly how the system behaves when all services operate concurrently. The successful
correlation between implemented structure and runtime validation confirms the viability of the
Krishi Vaidya platform.

\subsubsection{Reliability and Safety Interpretation}

Krishi Vaidya includes several reliability controls that are appropriate for an agricultural
advisory system. Images are validated before model calls. Backend diagnosis uses request IDs and
processing-time measurement. The VLM service is checked for readiness before inference. The VLM
gateway uses JWT scope validation. The advisory generator is required to return schema-valid JSON.
The mobile app handles cloud, cached, and queued outcomes. The result view uses structured fields
instead of raw model text.

These controls improve engineering safety, but they do not solve every agronomic safety problem.
Model uncertainty, class imbalance, field-image variability, pesticide recommendation risk,
out-of-distribution images, and incorrect crop hints can still affect final advice. The system
should therefore present confidence, uncertainty, retake guidance, safety warnings, and expert
consultation guidance where appropriate. The backend already includes confidence-tier and
out-of-distribution fields, which remain central to the app presentation and final claims.

\subsubsection{Current Limitations}

The current limitations fall into four groups: model limitations, validation limitations,
integration limitations, and manuscript-evidence limitations.

Model limitations are most visible in the VLM results. The VLM has low test accuracy and a high
number of parse errors. This limits the strength of claims that can be made about automatic
disease diagnosis. The YOLO model is stronger, demonstrating excellent bounding-box reliability
and perfect taxonomy alignment with the mobile application.

Validation limitations are visible mainly in automated test breadth. Backend scan tests are useful,
but equivalent tests remain limited across the remaining route groups and external diagnosis branches.
The mobile app has source-backed architecture, an inference harness, physical-device screenshots,
and completed workflow validation. Integration validation was successfully demonstrated through a
live distributed request cycle.

Integration limitations are tied to external services and runtime configuration. The backend
diagnosis route depends on the VLM service and Google AI advisory service being reachable and
properly configured. The advisory generator must return schema-valid JSON. The mobile app must be
configured with the correct API base URL and must handle network failure correctly. Offline sync
infrastructure exists, but complete two-way synchronization for every secondary local table
remains a future refinement.

Manuscript-evidence limitations are practical but important. While the live integration
was verified across Lightning.ai, Supabase, and ngrok, the manuscript should not claim
full production deployment or field-tested agronomic performance until large-scale user
studies and expert pathological reviews are conducted.

\subsubsection{Implications for Final Manuscript Claims}

The final claims must be strong where the evidence is strong and cautious where the evidence is
limited. The project can claim a modular Krishi Vaidya system with YOLO, VLM, backend, mobile,
and integration components. It can claim that YOLO and VLM datasets and outputs have been
analyzed and documented using available figures and tables. It can also claim that the backend
and mobile application contain complete, verified implemented architecture.

The evidence does not support claims that the current VLM model is already highly accurate, that
the mobile app has been agronomically field-tested, or that the system is scaled for production.
Those claims require expert agronomic validation, load testing, and broader automated test suites.
Maintaining this boundary strengthens the thesis because it shows a clear distinction between
implementation, evaluation, and deployment.
