\chapter{SYSTEM DESIGN}

\ChapterSection{Design}

Four components move the system from the requirements in Chapter~3 to a deployable diagnosis
pipeline: a YOLO detector for plant-part localization, a fine-tuned VLM for disease
classification, a backend that orchestrates inference and advisory generation, and a mobile
application that delivers results to the farmer. The sections below describe each component with its
datasets and configuration, followed by the algorithmic procedures that run across them.

\ChapterSubsection{YOLO Object-Detection Dataset}

Leaves, panicles, grain clusters, fruits, ears, and vegetable heads --- the YOLO component
localizes all of them within crop images. Disease classification belongs to the VLM. The
detector's role is more bounded: it tells the downstream pipeline which plant parts are
present and where they sit in the frame.

We chose YOLOv8 nano specifically because it is small enough for mobile TFLite export while

\subsubsection{Data Sources and Class Mapping}

Our sources span Kaggle and Roboflow datasets covering tomato, rice, potato, maize, brassica,
cauliflower, and cabbage imagery, merged into a single class taxonomy. From 34,992
candidate images, curation removed 4,011 images and 13,218 annotations flagged for
out-of-bounds coordinates, sub-pixel area, or collapse after clamping. This imbalance is
severe: rice panicle holds 115,046 of 147,467 annotations, while maize ear
(106) and rice grain cluster (473) are barely present. Aggregate mAP hides this.
Per-class metrics, shown in Figure~\ref{fig:yolo-data-pipeline-flow}, are the only way to
see the real distribution.

\ChapterSubsection{VLM Disease-Diagnosis Dataset}

Disease interpretation runs on Qwen2.5-VL-3B \parencite{bai2025qwen25vl}. Given a crop image
and a natural-language instruction, it returns a structured JSON diagnosis. At 3B
parameters with 4-bit LoRA fine-tuning, the model fits on a single L4 GPU. Since the output
is generated text rather than a fixed-vocabulary prediction, parseability becomes a first-class
evaluation metric alongside classification accuracy. Figure~\ref{fig:vlm-system-architecture-overview}
shows the architecture for this component.

\subsubsection{Taxonomy and Label Normalization}

Our taxonomy covers rice, maize, potato, tomato, cauliflower, and cabbage across eleven
disease classes: maize common rust, maize healthy, maize northern leaf blight, potato early
blight, potato healthy, potato late blight, tomato early blight, tomato healthy, tomato late
blight, tomato leaf mold, and tomato septoria leaf spot. Canonical labels follow the format
\texttt{crop\_\_disease} --- for example, \texttt{potato\_\_late\_blight}. Since evaluation
relies on exact canonical-label matching, alias normalization at export is a correctness
requirement, not a cosmetic one.

\subsubsection{Dataset Pipeline}

We configured the dataset pipeline under \texttt{vlm\_model/data/configs} as project
\texttt{krishivaidya}, dataset \texttt{kv-core5-ms}. Splits reserve 15\% for a locked test
set and 15\% for validation. Per-crop record caps prevent any single crop from dominating
training: 800 for rice, maize, potato, and tomato; 600 for cauliflower and cabbage
(Figure~\ref{fig:vlm-data-pipeline-flow}).

\subsubsection{Qwen2.5-VL SFT Export}

Each exported record pairs an image path with a human message that includes the image token and
instruction, an assistant answer, and metadata fields such as split, crop, disease, canonical
label, template id, and source. The assistant target takes one of three shapes:
\texttt{disease\_json} requests compact JSON with \texttt{crop}, \texttt{disease},
\texttt{canonical\_label}, and \texttt{confidence\_label}; \texttt{label\_only} asks for
just the canonical and confidence labels; \texttt{diagnostic\_short} adds a brief
visual-diagnosis sentence.

LoRA adapters target the attention and feed-forward projection layers, excluding visual
modules. Fine-tuning configuration and prediction parsing follow in Algorithm Details.

\ChapterSubsection{Backend System Architecture}

A TypeScript and Express API sits between the mobile client and every backend concern: farm
records, image storage, authentication, VLM inference, and advisory generation, all behind a
single versioned interface. Configuration, middleware, routing, controllers, services,
repositories, and data models each live in separate layers so that HTTP transport, business
rules, database persistence, and ML integrations do not leak into each other
\parencite{sculleyMLTechDebt2015}.

The request path, traced in Figure~\ref{fig:backend-architecture}, shows how the mobile app
sends JSON and multipart requests to Express, controllers validate inputs, services enforce
workflow rules, repositories wrap Mongoose queries, and models define MongoDB documents.

\subsubsection{Runtime Modes and Application Initialization}

Three runtime modes control which route groups load, set through the \texttt{BACKEND\_MODE}
environment variable: \texttt{diagnose} (model-serving routes only), \texttt{non\_ai} (database
routes only), and \texttt{complete} (all routes). A health endpoint at \texttt{/api/v1/health}
reports server state, uptime, environment, mode, and public base URL. Before the server
starts, Zod validates every configuration variable, preventing silent startup in an incomplete
state. Database-backed routes need JWT, Cloudinary, and SMTP credentials; the diagnosis stack
needs the ML service URL and its authentication configuration.

We wired all dependencies in \texttt{src/container.ts} --- repositories first, then services,
controllers, and route modules --- keeping the dependency graph in one place instead of
scattered across route files.

\subsubsection{Controller and Validation Pattern}

Each controller receives typed service dependencies and exposes Express request handlers. For
validation, we use \texttt{express-validator} to check MongoDB identifiers, bound pagination
values, enumerate types for task categories and advisory severities, and limit text-field
lengths. A shared response formatter sends back successful responses; a global error
middleware catches operational failures.

Most database-backed routes require authentication. On every protected route, the auth
middleware verifies a Bearer token against the configured JWT secret, rejects expired or
malformed tokens, blocks pending-verification and suspended accounts, and attaches the decoded
user context to the request. Service methods then enforce ownership through repository
queries, so access control does not repeat in every controller.

On the advisory side, we require a strict JSON response covering disease, confidence,

\ChapterSubsection{Backend Security, Uploads, and Reliability Controls}

\subsubsection{Upload Handling and Cloudinary Storage}

Multer memory storage handles incoming files, filtered by MIME type and extension against
JPEG, PNG, and WEBP. Scan images, profile pictures, and note images upload to
Cloudinary with secure URLs and automatic quality and format transformations. And if a profile
picture or note image gets replaced or removed, the backend deletes the previous Cloudinary
asset too.

\subsubsection{Request Safety and Error Handling}

Rate limits are set at 100 requests per 15 minutes for general routes, 10 per 15 minutes for
authentication routes, and 5 per hour for OTP routes. Errors of all kinds --- application
errors, Multer upload errors, Mongoose validation errors, duplicate-key errors, JWT errors ---
get folded into uniform JSON responses by a global error handler. In production, unknown errors
surface as a generic message; development mode exposes the full diagnostic detail.

\subsubsection{Authentication and Session Handling}

When a user logs in, they get a short-lived access token and a hashed refresh token stored
in an HTTP-only cookie. Refresh tokens carry lookup IDs, expiry timestamps, and revocation
state, supporting both single-session and all-session logout. For OTP, we store hashed values
with expiry and attempt counts under a unique email-purpose index, so each purpose --- email
verification, password reset, phone verification --- has its own expiration window.

\ChapterSubsection{Mobile Application Architecture}

\subsubsection{Purpose and Implementation Scope}

actions write to SQLite before synchronizing with the backend. Expo Router handles navigation,
TanStack Query manages server-state mutations, i18next provides bilingual content,
VisionCamera handles native capture, and TFLite runs on-device inference. The Android package
is \texttt{com.krishivaidya.app} under scheme \texttt{krishivaidya}

\subsubsection{Provider, Repository, and Dependency Structure}

Dependencies reach the component tree through two context providers. Camera, network,
notification, haptics, voice, and location services come from \texttt{ServicesProvider}.
Scans, crops, tasks, notes, and the data catalog come from \texttt{RepositoryProvider}. During
startup, the repository bootstrap initializes SQLite, runs the V3-to-V4 migration, performs a
one-time MMKV-to-SQLite migration, constructs datasources, creates repository instances, and
starts the offline sync manager. Agricultural catalog data --- varieties, growth stages,
fertilizer recommendations, disease entries, and seasonal tips --- ships as JSON fixtures,
separate from user records in SQLite.

\subsubsection{Validation and Threshold Selection}

Our validation pipeline reports precision, recall, F1-score, mAP@50, and mAP@50-95. mAP@50
evaluates detections at IoU 0.50; mAP@50-95 applies the COCO range from 0.50 to 0.95. A
confidence sweep from 0.05 to 0.95 selects the deployment threshold: lower values preserve
more detections but admit weaker predictions; higher values suppress weak detections but miss
more objects. The operating point is a precision--recall tradeoff, not a single-metric maximum.

\subsubsection{Export and Mobile Post-Processing}

The detector exports to FP32, FP16, and INT8 TFLite variants, keeping the same class taxonomy.
On device, the selected variant takes a 640-pixel RGB input. For each detection row, the
post-processor picks the highest class score, multiplies it by objectness to get confidence,
drops candidates below the confidence threshold, and runs non-maximum suppression at the
configured IoU threshold. Surviving boxes are returned with class id, class name, confidence,
and bounding-box coordinates.

\ChapterSubsection{VLM Fine-Tuning and Prediction-Parsing Procedure}

\subsubsection{Adapter Fine-Tuning}

We converted curated crop-disease records into Qwen-compatible prompt-response examples and
fine-tuned \texttt{Qwen/Qwen2.5-VL-3B-Instruct} with LoRA adapters
\parencite{hu2021lora}. Adapters target the attention and feed-forward projection layers:
\texttt{q\_proj}, \texttt{k\_proj}, \texttt{v\_proj}, \texttt{o\_proj},
\texttt{gate\_proj}, \texttt{up\_proj}, and \texttt{down\_proj}. Modules matching
\texttt{visual}, \texttt{vision}, or \texttt{merger} are excluded so that only language-side
weights are adapted.

\subsubsection{Prediction Parsing}

During inference, the gateway receives a crop image and a diagnosis prompt. The generated text
gets parsed as a complete JSON object first. If that fails, the parser tries extracting the
first embedded JSON object. A \texttt{canonical\_label} field, if present, becomes the
predicted label. Without one, we tag the prediction \texttt{\_\_parse\_error\_\_}. This prevents free-form text
from passing as a valid diagnosis and makes parseability part of model evaluation.

\ChapterSubsection{Backend Diagnosis-Orchestration Procedure}

\subsubsection{Request Validation and VLM Call}

\texttt{POST /api/v1/diagnose} accepts a multipart request with the image in the
\texttt{image} field and an optional crop-name hint. Validation checks file existence, upload
size, image headers, MIME consistency, dimensions, and format. We reject images outside
\(64 \times 64\) to \(4096 \times 4096\) pixels and cap the crop-name hint at
80 characters. We accept JPEG, PNG, and WEBP.

Once validated, the diagnosis service checks VLM gateway readiness at \texttt{/ready}. If the
gateway is unconfigured, unreachable, timed out, or not ready, the backend raises a
service-unavailable error rather than returning a partial result. Otherwise it sends an
authorized \texttt{/v1/inference} request with base64 image data, media type, request id,
deterministic generation settings, a 320-token output limit, and a crop-disease prompt.
Auth uses either a static bearer token or a cached RS256 JWT.

\subsubsection{Advisory Generation and Response Assembly}

Parsing the VLM prediction uses the JSON rules described above. From there, the backend
forwards the parsed context and validated image to the Google AI advisory client. The advisory
response must pass schema validation before acceptance. We clamp confidence to \([0, 1]\),
cap alternatives at three, and assign a confidence tier: \(\geq 0.85\) maps to high, 0.60--0.85
to medium, lower non-OOD values to low, and out-of-distribution or below 0.30 to OOD. The
assembled response carries request metadata, disease fields, symptoms, advisory content,
processing time, and model version.

\ChapterSubsection{Mobile Offline and Result-Handling Procedure}

\subsubsection{Scan State and Network Branching}

After image capture (or gallery selection), preview, optional editing, and quality review, the
analysis view model enters one of seven phases: \texttt{ready}, \texttt{scanning},
\texttt{reviewed}, \texttt{sending}, \texttt{success}, \texttt{failed}, or \texttt{queued}.
Network state determines the next step: online sends a cloud request; slow races the request
against a five-second timeout and falls back on failure; offline skips the backend and queues
the scan.

We write queued scans to SQLite scan history and the unified sync queue as
\texttt{scan\_diagnosis} entries. If a cached advisory for the crop context is available, it
fills in while the scan waits for cloud diagnosis. The API client applies a 60-second timeout
and retries transient failures (408, 429, 500, 502, 503, 504) with exponential backoff.

\subsubsection{Farmer-Facing Result Mapping}

Completed responses get mapped into bilingual disease details, confidence display, treatment
timelines, prevention advice, safety warnings, reminders, feedback, PDF export, and share
cards by the result view. Labels appear in Nepali or English based on the current language
preference. Treatment steps render as timeline items with optional organic alternatives. The
completed scan gets saved for later access from crop or history screens.
