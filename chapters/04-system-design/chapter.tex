\chapter{SYSTEM DESIGN}

\ChapterSection{Design}

The system design refines the analysis from Chapter~3 into four implementation components:
YOLO object detection, VLM disease interpretation, backend orchestration, and mobile delivery.
Each component is described in terms of its dataset or data model, its configuration, and its
role in the integrated diagnosis workflow.

\ChapterSubsection{YOLO Object-Detection Dataset}

The YOLO component localizes plant-part structures within crop images to contextualize
downstream diagnosis. Rather than yielding a standalone disease label, it identifies leaves,
panicles, grain clusters, fruits, ears, and vegetable heads for the VLM and advisory pipeline.

\subsubsection{Data Sources and Class Mapping}

Sources span Kaggle and Roboflow datasets covering tomato, rice, potato, maize, brassica,
cauliflower, and cabbage imagery, all merged into a single class taxonomy. From 34,992
candidate images, curation removed 4,011 images and 13,218 annotations flagged for
out-of-bounds coordinates, sub-pixel area, or collapse after clamping. The class distribution
is heavily skewed: rice panicle accounts for 115,046 of 147,467 annotations, while maize ear
(106) and rice grain cluster (473) are the least represented. This imbalance directly shapes
per-class validation behavior and cannot be read from aggregate precision or mAP alone.
The data pipeline flow is illustrated in Figure~\ref{fig:yolo-data-pipeline-flow}.

\subsubsection{Evaluation Metrics}

Validation uses precision, recall, F1-score, mAP@50, and mAP@50-95. mAP@50 evaluates
detections at a single IoU threshold of 0.50; mAP@50-95 applies the COCO range from 0.50
to 0.95. No single aggregate captures the full picture for a class-imbalanced, multi-scale
dataset, so the analysis combines aggregate metrics with threshold sensitivity, per-class
F1-score, deployment efficiency, and error categorization.

\subsubsection{Confidence Threshold Analysis}

A confidence sweep from 0.05 to 0.95 identifies the operating point that best balances
precision and recall for the mobile diagnosis context. Lower thresholds raise recall by
admitting weaker predictions; higher thresholds improve precision at the cost of missed
detections. The selected threshold is a deployment tradeoff, not a mathematical optimum on
any single metric.

\subsubsection{Deployment and Quantization Evaluation}

The deployment comparison evaluates the baseline PyTorch model against FP32, FP16, and INT8
TFLite variants across model size, compression ratio, latency, FPS, precision, recall, and
F1-score. Latencies were measured on \texttt{cuda:0} as a controlled format comparison;
on-device Android profiling confirms the mobile integration around the exported assets.

\ChapterSubsection{VLM Disease-Diagnosis Dataset}

Krishi Vaidya uses Qwen2.5-VL-3B as its disease-interpretation engine. Unlike the YOLO
detector, the VLM processes a full crop image alongside a natural-language instruction and
returns a structured diagnostic response \parencite{bai2025qwen25vl}. The 3B parameter scale
with 4-bit LoRA fine-tuning fits within a single L4-class GPU while remaining capable of
structured JSON generation. Because the output is generated text, evaluation must treat
structural parseability as a first-class metric alongside classification accuracy.
Figure~\ref{fig:vlm-system-architecture-overview} shows the overall architecture for the VLM component.

\subsubsection{Taxonomy and Label Normalization}

The taxonomy spans rice, maize, potato, tomato, cauliflower, and cabbage. The reported
training and evaluation outputs cover eleven classes: maize common rust, maize healthy, maize
northern leaf blight, potato early blight, potato healthy, potato late blight, tomato early
blight, tomato healthy, tomato late blight, tomato leaf mold, and tomato septoria leaf spot.
Canonical labels follow the format \texttt{crop\_\_disease}
(e.g., \texttt{potato\_\_late\_blight}). Evaluation uses exact canonical-label matching, so
alias normalization at export is a hard correctness requirement, not a cosmetic choice.

\subsubsection{Dataset Pipeline}

The VLM dataset pipeline is configured under \texttt{vlm\_model/data/configs} as project
\texttt{krishivaidya}, dataset \texttt{kv-core5-ms}. The split policy reserves 15\% for a
locked test set and 15\% for validation. Per-crop record caps --- 800 for rice, maize, potato,
and tomato; 600 for cauliflower and cabbage --- prevent any single source category from
dominating training. Figure~\ref{fig:vlm-data-pipeline-flow} illustrates the data pipeline flow.

\subsubsection{Qwen2.5-VL SFT Export}

Each exported record contains an image path, a human message with the image token and
instruction, an assistant answer, and metadata fields (split, crop, disease, canonical label,
template id, source). The \texttt{disease\_json} template asks for compact JSON with \texttt{crop},
\texttt{disease}, \texttt{canonical\_label}, and \texttt{confidence\_label}. The
\texttt{label\_only} template requests just the canonical and confidence labels. The
\texttt{diagnostic\_short} template adds a brief visual diagnosis sentence.

\ChapterSubsection{VLM Fine-Tuning Method}

\subsubsection{Base Model and Adapter Design}

Fine-tuning starts from \texttt{Qwen/Qwen2.5-VL-3B-Instruct} using LoRA adapters
\parencite{hu2021lora} applied to attention and feed-forward projection layers:
\texttt{q\_proj}, \texttt{k\_proj}, \texttt{v\_proj}, \texttt{o\_proj},
\texttt{gate\_proj}, \texttt{up\_proj}, and \texttt{down\_proj}. Modules matching
\texttt{visual}, \texttt{vision}, or \texttt{merger} are excluded, keeping adapter
targeting focused on the language components. Table~\ref{tab:vlm-finetuning-configuration}
lists the complete configuration.

\subsubsection{Quantized Training Configuration}

The model loads with 4-bit NF4 quantization, double quantization, bfloat16 compute dtype,
flash attention, and automatic device mapping. The three-epoch schedule reflects GPU compute
budget rather than a deliberate early stop: training consumed 12.56 GB of 22.03 GB available
on the L4 GPU. The Liger kernel was enabled; \texttt{torch.compile} was disabled.

\subsubsection{Evaluation and Prediction Parsing}

Evaluation runs on the held-out test split. For each record, the inference request contains
the image and user prompt; the expected label is resolved from record metadata or the assistant
target. The predicted label is extracted from generated JSON --- either a top-level parse or an
embedded JSON block within the output text. If no \texttt{canonical\_label} field is found,
the prediction is assigned \texttt{\_\_parse\_error\_\_}. A response that yields useful words
but no canonical label cannot be consumed by downstream backend code, so parseability is scored
as a component of model performance.

\ChapterSubsection{Backend System Architecture}

The backend is a TypeScript and Express API that orchestrates the mobile client, farm records,
image storage, authentication, VLM inference, and advisory generation through a single
versioned interface. A layered design separates configuration, middleware, routing, controllers,
services, repositories, and data models --- isolating HTTP transport, business rules, database
persistence, and external ML integrations from one another \parencite{sculleyMLTechDebt2015}.

Figure~\ref{fig:backend-architecture} shows the verified backend architecture. The mobile app
communicates with Express through JSON and multipart requests; controllers validate inputs,
services apply workflow rules, repositories isolate Mongoose queries, and models define
persisted MongoDB documents.

\subsubsection{Runtime Modes and Application Initialization}

The backend supports three runtime modes through the validated \texttt{BACKEND\_MODE}
environment variable: \texttt{diagnose} (AI routes only), \texttt{non\_ai} (database routes
only), and \texttt{complete} (all routes enabled). A health endpoint at
\texttt{/api/v1/health} reports server state, uptime, environment, mode, and the public base
URL. All configuration is Zod-validated before the server starts, preventing silent startup in
an incomplete state. Database-backed routes require JWT, Cloudinary, and SMTP credentials; the
diagnosis stack requires the ML service URL and authentication configuration.

\subsubsection{Dependency Container}

All dependencies are wired in \texttt{src/container.ts}: repositories first, then services,
controllers, and route modules. Explicit construction keeps the dependency graph visible and
avoids scattering object creation across route files.

\subsubsection{Controller and Validation Pattern}

Controllers receive typed service dependencies and expose Express request handlers.
Validation uses \texttt{express-validator} for MongoDB identifier checks, bounded pagination
values, enumerated types for task categories and advisory severities, and text field length
limits. Successful responses pass through a shared response formatter; operational failures are
forwarded to a global error middleware.

Most database-backed routes require authentication. The middleware verifies a Bearer access
token against the configured JWT secret, rejects expired or malformed tokens, blocks
pending-verification and suspended users, and attaches the decoded user context to the request.
Service methods can then enforce ownership through repository queries without repeating access
control in each controller.

\ChapterSubsection{Backend Diagnosis and Advisory Pipeline}

\subsubsection{Image Validation}

The diagnosis route accepts a single image via the multipart field \texttt{image}. The
validation service checks file existence, upload size, and image type by reading headers and
dimensions from the buffer directly --- bypassing MIME-type spoofing. Images outside the
\(64 \times 64\) to \(4096 \times 4096\) pixel range are rejected; the optional crop-name
hint is capped at 80 characters. Accepted formats are JPEG, PNG, and WEBP.

\subsubsection{VLM Inference Bridge}

\subsubsection{Google AI Advisory Bridge}

The parsed VLM output and the uploaded image are forwarded to the Google AI advisory client.
A strict JSON schema is required in the response, covering disease name, Nepali disease name,
scientific name, crop, confidence, confidence tier, out-of-distribution flag, symptom
descriptions, treatment steps, prevention tips, safety warnings, organic alternatives, source
URLs, and optional alternative diagnoses. The system prompt instructs the model to act as an
agricultural disease advisory expert for Nepali farmers, using both Nepali and English fields,
and to avoid unsafe pesticide advice and fabricated citations. Google Search grounding is
requested when enabled; if the model rejects the grounding tool, the client retries without
it. The returned JSON is Zod-validated before the final response is assembled.

\ChapterSubsection{Backend Security, Uploads, and Reliability Controls}

\subsubsection{Upload Handling and Cloudinary Storage}

Multer memory storage handles incoming files, filtered by MIME type and extension against
JPEG, PNG, and WEBP. Scan images, profile pictures, and note images are uploaded to Cloudinary
with secure URLs and automatic quality and format transformations. The backend also deletes
Cloudinary assets when existing profile pictures or note images are replaced or removed.

\subsubsection{Request Safety and Error Handling}

Rate limits are 100 requests per 15 minutes for general routes, 10 per 15 minutes for
authentication routes, and 5 per hour for OTP requests. The global error handler normalizes
application errors, Multer upload errors, Mongoose validation errors, duplicate-key errors,
and JWT errors into consistent JSON responses. In production, unknown errors surface as a
generic message; development mode exposes additional diagnostic detail.

\subsubsection{Authentication and Session Handling}

Login returns a short-lived access token and stores a refresh token in an HTTP-only cookie.
Refresh tokens are represented as hashed records with lookup IDs, expiry timestamps, and
revocation state, supporting both single-session and all-session logout. OTP records use
hashed values with expiry and attempt tracking under a unique email-purpose index, giving
each active OTP purpose a controlled lifecycle across email verification, password reset, and
phone verification flows.

\ChapterSubsection{Mobile Application Architecture}

\subsubsection{Purpose and Implementation Scope}

The mobile application is the primary farmer-facing interface, implemented with React Native
and Expo for cross-platform delivery \parencite{reactNativeDocs,expoDocs}. Its scope covers
onboarding, crop-plot management, offline-aware scan queuing, diagnosis submission, structured
result presentation, and localized record keeping. The design follows a local-first approach
\parencite{kleppmannLocalFirst2019}: user actions write to local storage immediately, with
backend synchronization handled separately. The stack uses Expo Router for navigation,
TanStack Query for server-state mutations, SQLite for local persistence, i18next for bilingual
content, VisionCamera for native capture, and TFLite for on-device inference. The Android
package is \texttt{com.krishivaidya.app} under scheme \texttt{krishivaidya}.

\subsubsection{Provider, Repository, and Dependency Structure}

The \texttt{ServicesProvider} exposes camera, network, notification, haptics, voice, and

tasks, notes, and the data catalog. The repository bootstrap initializes SQLite, runs the
V3-to-V4 migration, performs a one-time MMKV-to-SQLite migration, constructs datasources,
creates repository instances, and starts the offline sync manager. Read-only agricultural
catalog data --- varieties, growth stages, fertilizer recommendations, disease entries, and
seasonal tips --- is stored as JSON fixtures, kept separate from user-created records in SQLite.

\subsubsection{Scan Workflow and Diagnosis Flow}

The scan workflow is a deliberate multi-stage sequence. Native capture uses VisionCamera with
model overlay state, crop context, flash and torch control, zoom, and camera switching; a
web-compatible fallback exists. The preview stage runs image-quality analysis before the user
proceeds. The image-editor stage allows refinement before the submission.

The analysis view model runs an explicit state machine with phases \texttt{ready},
\texttt{scanning}, \texttt{reviewed}, \texttt{sending}, \texttt{success}, \texttt{failed}, and
\texttt{queued}. The network-aware diagnosis hook selects one of three execution paths: a cloud
request when online, a five-second race against timeout on slow connections, or an offline queue
when disconnected. The API client posts to \texttt{/api/v1/diagnose} with a 60-second timeout
and retries transient failures --- status codes 408, 429, 500, 502, 503, and 504 --- up to
three times with exponential backoff. The scan pipeline flow is illustrated in Figure~\ref{fig:mobile-scan-pipeline-flow}.

\subsubsection{Backend Orchestration Boundary}

The backend protects both the VLM service and the Google AI advisory client from direct mobile
exposure. The VLM client uses a cached RS256 JWT (or static bearer token) to authenticate with
the gateway, avoiding placement of inference credentials in the mobile application. If the
gateway is unreachable or not ready, the backend raises a service-unavailable error rather than
returning a partial result to the client.

\subsubsection{VLM Inference Gateway Boundary}

The VLM inference gateway is a FastAPI service \parencite{fastapiDocs} exposing
\texttt{/health}, \texttt{/ready}, and \texttt{/v1/inference}. Readiness succeeds only when
a vLLM client is active and the expected model is confirmed reachable. Inference requires JWT
authentication with the correct \texttt{inference} scope. Image data arrives as base64; the
gateway validates size, dimensions, format, and visual-token limits before forwarding validated
bytes and the prompt to vLLM. The response carries prediction text, latency in milliseconds,
token counts, model identifier, and timestamp.

\subsubsection{Prediction Parsing and Advisory Generation}

VLM output is parsed defensively: full JSON first, then an embedded JSON object, then raw text
as a fallback. Extracted fields include crop, disease name, canonical label, confidence (clamped
to \([0, 1]\)), and at most three alternatives. The parsed or raw context is then submitted to
the Google AI advisory client as described in the advisory bridge design. The Zod-validated
advisory response is merged with VLM prediction metadata to form the final diagnosis payload.

\subsubsection{Mobile Offline and Slow-Network Integration}

When offline, the app queues the scan in SQLite and the unified sync queue, inserting it into
scan history as a pending record. If a cached advisory exists, it can be returned immediately
while the scan awaits cloud diagnosis. On slow connections, the client races the cloud request
against a five-second timeout; if the request does not complete in time, the queue path takes
over. This behavior keeps the application functional in field conditions with unreliable
connectivity.

\subsubsection{Structured Response and Farmer-Facing Output}

The backend response includes request ID, timestamp, disease name and Nepali name, scientific
name, crop, numeric confidence, confidence tier, out-of-distribution flag, symptom descriptions,
advisory details, processing time, and model version. Confidence tiers: values at or above 0.85
are high; 0.60 to below 0.85 are medium; lower non-out-of-distribution values are low. A
response is out-of-distribution if the advisory model marks it as such or if confidence falls
below 0.30. Alternatives appear only for medium- and low-confidence responses. The mobile
result view maps treatment steps into a timeline, supports bilingual field switching, and saves
the completed scan to local history alongside PDF export, share-card, and feedback paths.

\subsubsection{Integration Verification Boundary}

Integration is verified through source inspection, contract review, and distributed runtime
execution --- with the VLM gateway deployed on Lightning.ai, the database on Supabase, and the
backend served via ngrok. Source review confirms the route contracts, validation checks,
inference gateway contract, advisory schema validation, mobile network branches, offline
queuing, and result-display mapping. VLM API tests cover health, readiness, authentication,
scope validation, invalid-image rejection, inference response mapping, error mapping, and
rate-limit behavior. Physical-device testing confirms the complete request lifecycle end to end.

\ChapterSection{Algorithm Details}

The preceding design section defines the system components, interfaces, and data flow. This
section isolates the execution procedures used by those components. Numeric results and
validation outcomes are reported in Chapter~5.

\ChapterSubsection{YOLO Detection and Deployment Procedure}

The detector procedure starts from the curated plant-part dataset. Image records and
bounding-box annotations are exported to YOLO format, trained with the YOLOv8 nano
configuration, and evaluated using detection metrics and confidence-threshold sweeps. The
selected detector is exported into FP32, FP16, and INT8 deployment variants without changing
the class taxonomy. On mobile, the selected TFLite variant runs on a 640-pixel RGB input,
filters candidates using the configured confidence threshold, and applies non-maximum
suppression using the configured IoU threshold before returning plant-part detections.

\ChapterSubsection{VLM Prediction-Parsing Procedure}

The VLM procedure converts curated crop-disease records into Qwen-compatible
prompt-response examples, fine-tunes Qwen2.5-VL-3B with LoRA adapters, and sends an image
and diagnosis prompt during inference. Generated text is parsed as full JSON first, then as an
embedded JSON object. If no canonical label can be extracted, the prediction is marked as
\texttt{\_\_parse\_error\_\_}; this prevents free-form text from being treated as a valid backend
diagnosis.

\ChapterSubsection{Backend Diagnosis-Orchestration Procedure}

For \texttt{POST /api/v1/diagnose}, the backend receives a multipart image request, validates
image type, size, and dimensions, checks VLM readiness, sends the authorized inference request,
parses the prediction, and passes the parsed context to the advisory client. The final response
is assembled only after schema validation and includes request metadata, confidence tier,
out-of-distribution status, advisory fields, processing time, and model version.

\ChapterSubsection{Mobile Offline and Result-Handling Procedure}

The mobile procedure begins with image capture or selection, preview, optional editing, and
image-quality review. The diagnosis hook selects an online request, a slow-network timeout
branch, or an offline queue branch. Offline scans are written to SQLite-backed history and sync
queues; when a cached advisory is available, it can be returned while the scan remains queued
for later cloud diagnosis. Completed responses are mapped into bilingual disease details,
treatment steps, reminders, feedback, PDF export, share-card output, and local scan history.
