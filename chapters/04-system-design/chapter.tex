\chapter{SYSTEM DESIGN}

\ChapterSection{Design}

The system design refines the analysis from Chapter~3 into four implementation components:
YOLO object detection, VLM disease interpretation, backend orchestration, and mobile delivery.
Each component is described in terms of its dataset or data model, its configuration, and its
role in the integrated diagnosis workflow.

\ChapterSubsection{YOLO Object-Detection Dataset}

The YOLO component localizes plant-part structures within crop images to contextualize
downstream diagnosis. Rather than yielding a standalone disease label, it identifies leaves,
panicles, grain clusters, fruits, ears, and vegetable heads for the VLM and advisory pipeline.

YOLOv8 nano was selected for its balance of mean average precision, inference latency, and
model footprint under lightweight deployment constraints
\parencite{jiangYOLOSurvey2022,ultralyticsYolov8}.
Figure~\ref{fig:yolo-system-architecture-overview} shows the overall architecture of this component.

\subsubsection{Data Sources and Class Mapping}

Sources span Kaggle and Roboflow datasets covering tomato, rice, potato, maize, brassica,
cauliflower, and cabbage imagery, all merged into a single class taxonomy. From 34,992
candidate images, curation removed 4,011 images and 13,218 annotations flagged for
out-of-bounds coordinates, sub-pixel area, or collapse after clamping. The class distribution
is heavily skewed: rice panicle accounts for 115,046 of 147,467 annotations, while maize ear
(106) and rice grain cluster (473) are the least represented. This imbalance directly shapes
per-class validation behavior and cannot be read from aggregate precision or mAP alone.
The data pipeline flow is illustrated in Figure~\ref{fig:yolo-data-pipeline-flow}.

\ChapterSubsection{YOLO Detector Design}

The YOLO detector is designed as a lightweight plant-part localization component rather than a
final disease classifier. Its design decisions are the use of the YOLOv8 nano architecture,
the eleven-class plant-part taxonomy, 640-pixel model input, and export targets compatible with
mobile TFLite deployment. The training, threshold selection, export, and mobile post-processing
steps are described under Algorithm Details.

\ChapterSubsection{VLM Disease-Diagnosis Dataset}

Krishi Vaidya uses Qwen2.5-VL-3B as its disease-interpretation engine. Unlike the YOLO
detector, the VLM processes a full crop image alongside a natural-language instruction and
returns a structured diagnostic response \parencite{bai2025qwen25vl}. The 3B parameter scale
with 4-bit LoRA fine-tuning fits within a single L4-class GPU while remaining capable of
structured JSON generation. Because the output is generated text, evaluation must treat
structural parseability as a first-class metric alongside classification accuracy.
Figure~\ref{fig:vlm-system-architecture-overview} shows the overall architecture for the VLM component.

\subsubsection{Taxonomy and Label Normalization}

The taxonomy spans rice, maize, potato, tomato, cauliflower, and cabbage. The reported
training and evaluation outputs cover eleven classes: maize common rust, maize healthy, maize
northern leaf blight, potato early blight, potato healthy, potato late blight, tomato early
blight, tomato healthy, tomato late blight, tomato leaf mold, and tomato septoria leaf spot.
Canonical labels follow the format \texttt{crop\_\_disease}
(e.g., \texttt{potato\_\_late\_blight}). Evaluation uses exact canonical-label matching, so
alias normalization at export is a hard correctness requirement, not a cosmetic choice.

\subsubsection{Dataset Pipeline}

The VLM dataset pipeline is configured under \texttt{vlm\_model/data/configs} as project
\texttt{krishivaidya}, dataset \texttt{kv-core5-ms}. The split policy reserves 15\% for a
locked test set and 15\% for validation. Per-crop record caps --- 800 for rice, maize, potato,
and tomato; 600 for cauliflower and cabbage --- prevent any single source category from
dominating training. Figure~\ref{fig:vlm-data-pipeline-flow} illustrates the data pipeline flow.

\subsubsection{Qwen2.5-VL SFT Export}

Each exported record contains an image path, a human message with the image token and
instruction, an assistant answer, and metadata fields (split, crop, disease, canonical label,
template id, source). The \texttt{disease\_json} template asks for compact JSON with \texttt{crop},
\texttt{disease}, \texttt{canonical\_label}, and \texttt{confidence\_label}. The
\texttt{label\_only} template requests just the canonical and confidence labels. The
\texttt{diagnostic\_short} template adds a brief visual diagnosis sentence.

\ChapterSubsection{VLM Adapter Design}

The VLM component is designed around Qwen2.5-VL-3B-Instruct, structured Qwen-format
image-text records, and LoRA adapter fine-tuning. The adapter design targets attention and
feed-forward projection layers while excluding visual modules, keeping trainable parameters
focused on language-side adaptation. The quantized fine-tuning and prediction-parsing
procedure is described under Algorithm Details.

\ChapterSubsection{Backend System Architecture}

The backend is a TypeScript and Express API that orchestrates the mobile client, farm records,
image storage, authentication, VLM inference, and advisory generation through a single
versioned interface. A layered design separates configuration, middleware, routing, controllers,
services, repositories, and data models --- isolating HTTP transport, business rules, database
persistence, and external ML integrations from one another \parencite{sculleyMLTechDebt2015}.

Figure~\ref{fig:backend-architecture} shows the verified backend architecture. The mobile app
communicates with Express through JSON and multipart requests; controllers validate inputs,
services apply workflow rules, repositories isolate Mongoose queries, and models define
persisted MongoDB documents.

\subsubsection{Runtime Modes and Application Initialization}

The backend supports three runtime modes through the validated \texttt{BACKEND\_MODE}
environment variable: \texttt{diagnose} (AI routes only), \texttt{non\_ai} (database routes
only), and \texttt{complete} (all routes enabled). A health endpoint at
\texttt{/api/v1/health} reports server state, uptime, environment, mode, and the public base
URL. All configuration is Zod-validated before the server starts, preventing silent startup in
an incomplete state. Database-backed routes require JWT, Cloudinary, and SMTP credentials; the
diagnosis stack requires the ML service URL and authentication configuration.

\subsubsection{Dependency Container}

All dependencies are wired in \texttt{src/container.ts}: repositories first, then services,
controllers, and route modules. Explicit construction keeps the dependency graph visible and
avoids scattering object creation across route files.

\subsubsection{Controller and Validation Pattern}

Controllers receive typed service dependencies and expose Express request handlers.
Validation uses \texttt{express-validator} for MongoDB identifier checks, bounded pagination
values, enumerated types for task categories and advisory severities, and text field length
limits. Successful responses pass through a shared response formatter; operational failures are
forwarded to a global error middleware.

Most database-backed routes require authentication. The middleware verifies a Bearer access
token against the configured JWT secret, rejects expired or malformed tokens, blocks
pending-verification and suspended users, and attaches the decoded user context to the request.
Service methods can then enforce ownership through repository queries without repeating access
control in each controller.

The advisory bridge is designed to require a strict JSON response containing disease,

\ChapterSubsection{Backend Security, Uploads, and Reliability Controls}

\subsubsection{Upload Handling and Cloudinary Storage}

Multer memory storage handles incoming files, filtered by MIME type and extension against
JPEG, PNG, and WEBP. Scan images, profile pictures, and note images are uploaded to Cloudinary
with secure URLs and automatic quality and format transformations. The backend also deletes
Cloudinary assets when existing profile pictures or note images are replaced or removed.

\subsubsection{Request Safety and Error Handling}

Rate limits are 100 requests per 15 minutes for general routes, 10 per 15 minutes for
authentication routes, and 5 per hour for OTP requests. The global error handler normalizes
application errors, Multer upload errors, Mongoose validation errors, duplicate-key errors,
and JWT errors into consistent JSON responses. In production, unknown errors surface as a
generic message; development mode exposes additional diagnostic detail.

\subsubsection{Authentication and Session Handling}

Login returns a short-lived access token and stores a refresh token in an HTTP-only cookie.
Refresh tokens are represented as hashed records with lookup IDs, expiry timestamps, and
revocation state, supporting both single-session and all-session logout. OTP records use
hashed values with expiry and attempt tracking under a unique email-purpose index, giving
each active OTP purpose a controlled lifecycle across email verification, password reset, and
phone verification flows.

\ChapterSubsection{Mobile Application Architecture}

\subsubsection{Purpose and Implementation Scope}

The mobile application is the primary farmer-facing interface, implemented with React Native
and Expo for cross-platform delivery \parencite{reactNativeDocs,expoDocs}. Its scope covers
onboarding, crop-plot management, offline-aware scan queuing, diagnosis submission, structured
result presentation, and localized record keeping. The design follows a local-first approach
\parencite{kleppmannLocalFirst2019}: user actions write to local storage immediately, with
backend synchronization handled separately. The stack uses Expo Router for navigation,
TanStack Query for server-state mutations, SQLite for local persistence, i18next for bilingual
content, VisionCamera for native capture, and TFLite for on-device inference. The Android
package is \texttt{com.krishivaidya.app} under scheme \texttt{krishivaidya}.

The integrated workflow design defines the boundary between mobile scan handling, backend

\subsubsection{Backend Orchestration Boundary}

The backend protects both the VLM service and the Google AI advisory client from direct mobile
exposure. Its design role is to receive a validated mobile request, isolate external service
credentials, enforce schema checks, and return one stable response contract to the mobile
application.

\subsubsection{VLM Inference Gateway Boundary}

The VLM inference gateway is a FastAPI service \parencite{fastapiDocs} exposing
\texttt{/health}, \texttt{/ready}, and \texttt{/v1/inference}. Its design role is to separate
model-serving infrastructure from the Express backend while enforcing readiness, authentication,
image-validation, and response-metadata boundaries.

\subsubsection{Prediction Parsing and Advisory Generation}

Prediction parsing and advisory generation are separated into two boundaries. The parser
normalizes model text into backend-readable context, while the advisory client converts that
context into the schema accepted by the mobile application. The detailed parsing and response
assembly rules are described under Algorithm Details.

\subsubsection{Mobile Offline and Slow-Network Integration}

The mobile offline design separates user-facing scan progress from backend availability.
SQLite-backed scan history, offline queues, cached advisory records, and sync-queue entries
allow the app to preserve work when network conditions are poor. The exact branch logic is
described under Algorithm Details.

\subsubsection{Structured Response and Farmer-Facing Output}

The structured response design gives the mobile application a stable contract instead of raw
model output. The response contract includes disease identity, confidence state, symptoms,
advisory content, processing metadata, and model version, with bilingual fields where required
by the farmer-facing interface.

\subsubsection{Validation and Threshold Selection}

Validation uses precision, recall, F1-score, mAP@50, and mAP@50-95. mAP@50 evaluates
detections at a single IoU threshold of 0.50, while mAP@50-95 applies the COCO range from
0.50 to 0.95. A confidence sweep from 0.05 to 0.95 is used to select a deployment threshold
for the mobile diagnosis context. Lower thresholds preserve more detections but admit weaker
predictions; higher thresholds remove weak detections but increase missed objects. The
operating point is therefore treated as a precision--recall tradeoff rather than a single
metric maximum.

\subsubsection{Export and Mobile Post-Processing}

After training and validation, the detector is exported into FP32, FP16, and INT8 TFLite
variants without changing the class taxonomy. On mobile, the selected TFLite variant runs on a
640-pixel RGB input. The raw output is scanned per detection row, the highest class score is
selected, objectness is multiplied by that class score to compute confidence, candidates below
the configured confidence threshold are removed, and non-maximum suppression filters
overlapping boxes using the configured IoU threshold. The remaining boxes are returned as
plant-part detections with class id, class name, confidence, and bounding-box coordinates.

\ChapterSubsection{VLM Fine-Tuning and Prediction-Parsing Procedure}

\subsubsection{Adapter Fine-Tuning}

The VLM procedure converts curated crop-disease records into Qwen-compatible prompt-response
examples, then fine-tunes \texttt{Qwen/Qwen2.5-VL-3B-Instruct} using LoRA adapters
\parencite{hu2021lora}. Adapter targets are attention and feed-forward projection layers:
\texttt{q\_proj}, \texttt{k\_proj}, \texttt{v\_proj}, \texttt{o\_proj},
\texttt{gate\_proj}, \texttt{up\_proj}, and \texttt{down\_proj}. Modules matching
\texttt{visual}, \texttt{vision}, or \texttt{merger} are excluded, keeping adapter training
focused on language-side adaptation.

The model loads with 4-bit NF4 quantization, double quantization, bfloat16 compute dtype,
flash attention, and automatic device mapping. The three-epoch schedule reflects the available
GPU budget rather than a deliberate early stop: training consumed 12.56 GB of 22.03 GB
available on the L4 GPU. The Liger kernel is enabled; \texttt{torch.compile} is disabled.

\subsubsection{Prediction Parsing}

During inference, the request contains the crop image and a diagnosis prompt. Generated text is
parsed as a complete JSON object first. If that fails, the parser extracts and parses the first
embedded JSON object. If a \texttt{canonical\_label} field is available, that value becomes the
predicted label. If no canonical label can be extracted, the prediction is assigned
\texttt{\_\_parse\_error\_\_}. This rule prevents free-form text from being treated as a valid
backend diagnosis and makes parseability part of model evaluation.

\ChapterSubsection{Backend Diagnosis-Orchestration Procedure}

\subsubsection{Request Validation and VLM Call}

For \texttt{POST /api/v1/diagnose}, the backend receives a multipart request with the image in
the \texttt{image} field and an optional crop-name hint. The validation service checks file
existence, upload size, image headers, MIME consistency, dimensions, and supported formats.
Images outside the \(64 \times 64\) to \(4096 \times 4096\) pixel range are rejected; the
crop-name hint is capped at 80 characters. Accepted formats are JPEG, PNG, and WEBP.

After validation, the diagnosis service checks VLM gateway readiness through \texttt{/ready}.
If the gateway is not configured, unreachable, timed out, or not ready, the backend raises a
service-unavailable error rather than returning a partial diagnosis. If ready, the backend
sends an authorized \texttt{/v1/inference} request containing base64 image data, media type,
request id, deterministic generation settings, a 320-token output limit, and a compact
crop-disease prompt. Authentication uses either a static bearer token or a cached RS256 JWT.

\subsubsection{Advisory Generation and Response Assembly}

The backend parses the VLM prediction using the JSON rules described above and forwards the
parsed or raw context, together with the validated image, to the Google AI advisory client. The
advisory response must satisfy the configured schema before it is accepted. Confidence is
clamped to \([0, 1]\), alternatives are limited to at most three items, and confidence tier is
computed from the advisory confidence and out-of-distribution flag: values at or above 0.85
are high, 0.60 to below 0.85 are medium, lower non-out-of-distribution values are low, and
out-of-distribution or confidence below 0.30 is marked OOD. The final response includes request
metadata, disease fields, symptoms, advisory fields, processing time, and model version.

\ChapterSubsection{Mobile Offline and Result-Handling Procedure}

\subsubsection{Scan State and Network Branching}

The mobile procedure begins with image capture or gallery selection, preview, optional editing,
and image-quality review. The analysis view model uses the phases \texttt{ready},
\texttt{scanning}, \texttt{reviewed}, \texttt{sending}, \texttt{success}, \texttt{failed}, and
\texttt{queued}. When the network state is online, the diagnosis hook sends a cloud request.
When the network state is slow, it races the cloud request against a five-second timeout and
falls back if the request does not finish. When offline, it skips the backend call and queues
the scan directly.

Queued scans are written to SQLite-backed scan history and to the unified sync queue as
\texttt{scan\_diagnosis} work. If a cached advisory is available for the crop context, it can
be returned while the scan remains queued for later cloud diagnosis. The API client uses a
60-second timeout for diagnosis requests and retries transient failures such as 408, 429, 500,
502, 503, and 504 with exponential backoff.

\subsubsection{Farmer-Facing Result Mapping}

Completed responses are mapped into bilingual disease details, confidence display, treatment
steps, prevention advice, safety warnings, reminders, feedback, PDF export, share-card output,
and local scan history. The result view selects Nepali or English labels from the current
language preference, maps treatment steps into timeline items, supports organic alternative
display, and saves the completed scan so it can be revisited from crop or history screens.
